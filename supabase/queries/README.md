# Course analytics queries

Paste any of these into the Supabase SQL editor and run it. Each file is one
self-contained statement — nothing to create or run first — and the editor's
CSV button exports the result as a table.

| File | One row per |
| --- | --- |
| `all_courses.sql` | course — subject, subcategory, title, and every metric. The master export. |
| `top_courses.sql` | the ten most-read |
| `by_subject.sql` | subject (6) |
| `by_subcategory.sql` | subcategory (18) |

`all_courses.sql` is the one to start from if you want to slice the data
yourself: export it once and pivot it in a spreadsheet by subject, by
subcategory, by completion rate, by anything else in there. The aggregates are
there for convenience, not because they hold anything the export does not.

They are generated by `scripts/build_course_titles_sql.py`. Supabase holds none
of the catalogue — not the title, not the subject, not the lesson count, all of
which ship inside the app — so the script inlines the 238 courses into each
query as a `values` CTE. Re-run it when the catalogue changes.

## What the columns mean

| Column | Meaning |
| --- | --- |
| `readers` | users who advanced at least one lesson |
| `finishers` | users who reached the end |
| `completion_pct` | `finishers / readers` |
| `avg_lessons_read` | furthest lesson reached, averaged, counting from 1 |
| `avg_progress_pct` | the same against that course's own length |
| `saves` | users with the course in their favourites right now |
| `quiz_takers` / `avg_quiz_score` | users who scored on the quiz, and their best score averaged |

`readers` counts a user who tapped "continue" at least once. `ProgressManager`
writes a `courseProgress` entry on that tap, not when the course opens, so a
course opened and closed on its first page is in nobody's count.

## What this data cannot tell you

**Nothing per language.** The reading language is stored nowhere: not in
`user_progress`, not in `profiles`, which holds only `id` and `handle`. Adding
the field to the progress snapshot is a small change on both platforms, but
until it ships and users sync again there is nothing to group by.

**Signed-in users only.** Sync never runs for anonymous users, so the whole set
covers accounts, not installs. Run the coverage query below before reading
anything into a ranking.

**Distinct users, not volume.** A course read ten times by one person counts
once. The snapshot keeps no history — no dates, no repeat counts, and no trace
of a course saved and then unsaved. An event log is what would answer those,
and it does not exist yet.

```sql
-- How many accounts the numbers above actually cover.
select
  count(*) as synced_users,
  count(*) filter (
    where up.progress::jsonb -> 'courseProgress' <> '{}'::jsonb
  ) as users_with_a_read,
  sum(jsonb_array_length(
    coalesce(up.progress::jsonb -> 'favoriteCourseIds', '[]'::jsonb)
  )) as total_saves
from user_progress up;
```
